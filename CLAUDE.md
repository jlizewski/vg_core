# vg_core: notes for Claude

vg_core maps outdoor spaces (a garden) from Android ARCore recordings (MCAP)
and turns them into maps for growing: ground, terrain, objects, canopy, sun.
It is a C++17 library plus command-line apps, with Python development tools.
The phone app lives in a separate repo, vg_android, which uses vg_core as a
submodule; a separate cloud agent works there. Sync with it through git, the
submodule and GitHub issues (draft the issue text; the user posts it).

## Working conventions

- **Branches:** `feat/<topic>`, `bug/<topic>` or `refactor/<topic>`. Check the
  current branch before starting: the user merges and switches between turns.
  Keep separate pieces of work (e.g. a bug fix found along the way) on their
  own branches.
- **Never commit unless asked. Never push unless asked.** Make the change, run
  the tests, report, and offer to commit.
- **Measure before building.** Prototype on real recordings (scratch Python is
  fine), report numbers, then build it into vg_core. Prefer small, measurable
  iterations with diagnostics over big rewrites.
- **Python tools that analyze recordings belong in the repo** (`tools/vg_tools`,
  run as `vg ...`), in some form, so the user can look too.
- Write code like the surrounding code: comment density, naming, idiom.
  Comments explain why, in plain sentences.

## Design principles

- **Mapping is the core feature**; everything else (sun, ground, objects) works
  off it, and it improves little by little.
- **The 3D voxel map (TSDF) is the core map.** Every other map is a stage
  derived from it, re-runnable from the saved map alone without the recording
  (`vg map <package> <stage>`). Keep stages modular, with clear inputs and
  outputs, so they can be swapped, reordered or rewired.
- **Tunable parameters go in YAML** (`config/mapping.yaml`, generated by
  `vg config defaults > config/mapping.yaml`; a test checks it's current).
  CLI flags and `--set path=value` override it. To add a setting: a field in
  the options struct, a binding in `src/config/mapping_config.cpp`, then
  regenerate the YAML.
- **2D maps use 6 in (0.1524 m) cells; voxels are 3 in.**
- **Everything runs on the phone. No cloud services** (no Cloud Anchors,
  Geospatial/VPS, servers), even at some cost in accuracy. GPS, sensors,
  map-to-map registration and user taps are fair game.

## Building and testing

- `vg build`, `vg test` (C++; `--preset release` for speed), `pytest tools`,
  `ruff check tools`. The Python venv is `tools/.venv` (`pip install -e
  "tools[dev,analysis]"`). On Windows the release build is in
  `build/release/Release/` and the tests in `build/release/tests/Release/`.
- C++ apps run as `vg <name>` (`apps/vg_<name>.cpp`); `vg` builds them in the
  release preset first. Main ones: `vg replay` (recording -> map package),
  `vg map` (re-run stages), `vg site` (line up walks), `vg mcap stats`,
  `vg segment`, `vg dashboard` (browser UI for all of it).
- Windows gotchas: scripts written through bash heredocs mangle backslash
  escapes; write them with a file instead. Python's default text encoding on
  Windows is cp1252, so pass `encoding="utf-8"` (README.md has non-ASCII).
  Windows Python can't open `/c/...` paths; use `C:/...`.

## Architecture in brief

- Recording format: `docs/capture-format.md` (depth, confidence, semantic
  labels, poses, GPS; z-up world).
- Map package (`include/vg_core/map_package.hpp`): `map.vgm` (TSDF + per-voxel
  label votes) plus stages: voxels, surface, ground, terrain, sky, sun,
  semantic, layers. Built by `vg::io::build_map_package`.
- Semantic labels: classes unknown, ground, plant, tree, structure, sky,
  dynamic (`semantics.hpp`); segmentation in vg_core (`segmentation.hpp`,
  ONNX Runtime on the desktop).
- Terrain (`terrain.hpp`): smooth contour from seen ground plus the walked path
  (phone height ~1.5 m is evidence of the ground under overgrowth).
- Sites (`site.hpp`, `registration.hpp`): many walks of one place in one frame.
  4-DOF registration: FFT search over feature outlines, then ICP on voxels
  standing over the terrain; GPS heading and position only break ties between
  alignments; ambiguous fits are refused, because a misplaced walk misleads
  every later one.
- Sky (`sky.hpp`): canopy beyond depth's reach, carved from sky-labeled rays;
  evidence `sky.vgs` per walk, combined per site.

## Where things stand (2026-11-13)

- Merged to main: semantic ground, desktop segmentation, terrain, sites.
  On branches awaiting merge: `feat/sky` (canopy), then `feat/dashboard`
  (stacked on it).
- Measured: walks of the whole yard line up with or without GPS, also a month
  apart (~0.5 m and ~2 degrees of disagreement: each walk drifts). Sweeps of a
  single thing (shed, house, canopy) only line up with GPS. The site-level
  canopy predicts held-out sky better than a horizon profile, most under the
  canopy and near the house.
- Next candidates: the sun stage using the canopy as shade; trimming
  `sky.vgs` (27 MB per 5-minute walk); fusing walks into one map, which needs
  per-walk drift correction first.
- App changes the work implies (to raise with vg_android): a site as the unit
  with a full yard loop first; registration right after each walk with
  accept/refuse feedback; a short loop before single-object sweeps; walk
  intent in the session notes; prompts to look up for canopy; stamp the depth
  calibration at or before the first depth frame.
- **Before shipping the app, re-evaluate the segmentation model** (license:
  ADE20K and NVIDIA's SegFormer weights are non-commercial; accuracy on yards;
  phone cost). The TODO is in `semantics.hpp` and the README. Raise it whenever
  release comes up.
